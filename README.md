# DailyGrow — сбор отзывов с Яндекс.Карт

Сервис для сбора и просмотра отзывов организаций с Яндекс.Карт: пользователь добавляет ссылку на организацию, запускает асинхронный сбор отзывов и просматривает результат с пагинацией и метриками (рейтинг, количество оценок, количество отзывов).

Разработан по методологии SDD (Spec-Driven Development). Полная документация процесса:

- [.sdd/spec.md](.sdd/spec.md) — функциональная спецификация (user stories, бизнес-правила парсинга, edge cases).
- [.sdd/plan.md](.sdd/plan.md) — техническое проектирование (схема БД, стратегия парсинга, API, архитектура фронтенда, NFR).
- [.sdd/tasks.md](.sdd/tasks.md) — декомпозиция на задачи по фазам с чек-листом выполнения.

## Структура монорепозитория

```
.
├── backend/    Laravel 11 API: Sanctum SPA-аутентификация, парсинг через очереди, MySQL
├── frontend/   Vue 3 + Vite SPA: Pinia, Vue Router, Axios
└── .sdd/       Спецификация, план и чек-лист задач (см. ссылки выше)
```

Проект развёртывается **без Docker** — только локально установленные PHP, Composer, Node.js и MySQL.

## Быстрый старт (3 терминала)

Backend, очередь и frontend — три независимых процесса. Все команды ниже выполняются из **корня репозитория**, если не указано иное.

### Предварительные требования

- PHP 8.2+ с Composer
- Node.js 18+ с npm
- Локальный MySQL-сервер, доступный на `127.0.0.1:3306`

### Терминал 1 — Backend (`php artisan serve`)

```bash
cd backend
composer install
cp .env.example .env
php artisan key:generate
```

Проверьте/поправьте в `backend/.env` подключение к MySQL (по умолчанию уже настроено под тестовую БД из ТЗ):

```
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=DailyGrowTestLaravel
DB_USERNAME=mysql
DB_PASSWORD=mysql
```

Создайте базу данных, если её ещё нет:

```sql
CREATE DATABASE DailyGrowTestLaravel CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Накатите миграции и сиды:

```bash
php artisan migrate --seed
```

Сидер создаёт единственного пользователя для входа: **`admin@example.com` / `password`** (переопределяются через `SEED_USER_EMAIL` / `SEED_USER_PASSWORD` в `.env`).

Запустите сервер разработки:

```bash
php artisan serve
```

Backend поднимется на `http://localhost:8000`.

### Терминал 2 — Очередь (`php artisan queue:work`)

Парсинг выполняется асинхронно через Laravel Queue (`ParseYandexCompanyJob`, очередь `parsing`, драйвер `database`). **Без отдельно запущенного воркера очереди сбор отзывов не продвинется дальше статуса `pending`** — задание будет создано и лежать в таблице `jobs`, но никто не возьмёт его в обработку.

```bash
cd backend
php artisan queue:work --queue=parsing
```

Оставьте этот терминал открытым на всё время работы с приложением. Если запустить парсинг через UI и не увидеть перехода `pending → processing → completed/failed`, первым делом проверьте, что этот процесс запущен.

### Терминал 3 — Frontend (`npm run dev`)

```bash
cd frontend
npm install
cp .env.example .env   # при необходимости поправьте VITE_API_BASE_URL
npm run dev
```

Frontend поднимется на `http://localhost:5173` и обращается к backend по адресу из `VITE_API_BASE_URL` (по умолчанию `http://localhost:8000`).

### CORS и Sanctum

Backend уже настроен на связку портов `5173` (frontend) / `8000` (backend) по умолчанию:

- `backend/.env`: `FRONTEND_URL=http://localhost:5173`, `SANCTUM_STATEFUL_DOMAINS=localhost:5173,127.0.0.1:5173`.
- `backend/config/cors.php`: `allowed_origins` берётся из `FRONTEND_URL`, `supports_credentials => true`.

Если меняете порт Vite или адрес backend, поправьте эти значения синхронно на обеих сторонах — иначе браузер будет блокировать запросы политикой CORS, а сессия Sanctum не установится как «доверенная» (см. «Известные ограничения» про `Origin`/`Referer`).

### Проверка полного пути

1. Откройте `http://localhost:5173` → редирект на `/login`.
2. Войдите как `admin@example.com` / `password`.
3. На дашборде добавьте ссылку вида `https://yandex.ru/maps/org/.../123456/`.
4. Нажмите «Запустить сбор отзывов» — статус перейдёт в «В очереди», затем (при запущенном `queue:work`) в «Собираем отзывы…» и, наконец, в «Готово» или «Ошибка».
5. Просмотрите собранные отзывы с пагинацией по 50 штук на странице.

## Пять дополнительных технических вопросов из ТЗ

### 1. Устойчивость к смене разметки источника

Проблема в том, что у Яндекс.Карт нет публичного API отзывов — используется реверс-инжиниринг внутренних JSON-эндпоинтов страницы. Если Яндекс поменяет формат ответа (переименует поле, изменит структуру пагинации), наивный парсер молча вернёт `0` отзывов, и это будет выглядеть как «у организации нет отзывов», а не как «парсер сломался». Это два принципиально разных случая, и путать их нельзя — иначе никто не заметит деградацию, пока не станет слишком поздно.

Решение реализовано на двух уровнях (`app/Services/Parsing/HttpJsonStrategy.php`, `app/Services/YandexMapParserService.php`):

- **Структурная проверка на уровне HTTP-стратегии.** Каждый ответ от карточки организации и от списка отзывов проверяется на наличие ожидаемых ключей (`name` у карточки, `reviews`/`id` у отзыва). Если ключа нет — это не «пустой результат», а признак того, что контракт ответа изменился. Бросается `ParsingStructureChangedException` немедленно, до того, как код успеет интерпретировать `null` как «отзывов нет».
- **Бизнес-правило на уровне сервиса.** Даже если JSON синтаксически валиден и все ключи на месте, есть более тонкий кейс: карточка организации сообщает `ratingCount > 0` (то есть оценки точно есть), а список отзывов вернул пустой массив. Это тоже признак поломки (например, отзывы теперь возвращаются с другой пагинацией или под другим фильтром), а не «отзывов действительно ноль». `YandexMapParserService::fetchReviews()` явно сравнивает счётчик с фактически собранным количеством и бросает то же исключение, если пришло `0` при заявленных `> 0`. Обратный случай (`ratingCount = 0` и `0` отзывов) — штатное завершение, не ошибка.

Дальше по конвейеру (`app/Jobs/ParseYandexCompanyJob.php`) исключение классифицируется отдельным типом ошибки `structure_changed` (в отличие от `banned`/`timeout`/`not_found`) и:

- записывается в `parsing_logs.error_type` + `error_message` — то есть в базе остаётся история именно структурных сбоев, отдельно от временных сетевых проблем;
- помечается как **не подлежащее автоматическому повтору** (`ParsingStructureChangedException::isRetryable() === false`, обработка через `$this->fail($e)` в Job) — повторная попытка того же запроса ничего не изменит, пока не обновится код парсера, поэтому не тратим ресурсы очереди на бессмысленные ретраи;
- отображается пользователю в UI как статус «Ошибка» с текстом причины (`ParsingStatusBadge.vue`).

Что было бы правильным добавить при наличии времени: отдельный алерт/уведомление разработчику (лог-канал, вебхук) именно на `error_type = structure_changed`, поскольку это единственный тип сбоя, который сигнализирует не о временной проблеме, а о необходимости чинить код.

### 2. Обоснование подхода к парсингу: HTTP JSON vs Headless-браузер

Рассматривались два подхода, подробное сравнение — в [plan.md §1.2](.sdd/plan.md#12-parsing-strategy).

| Критерий | HTTP JSON (перехват внутренних эндпоинтов) | Headless-браузер (Playwright/Puppeteer) |
|---|---|---|
| Скорость | Один быстрый HTTP-запрос + разбор JSON, десятки–сотни мс | Полный рендеринг страницы с JS-движком, обычно 5–10× дороже по CPU/RAM и по времени на один воркер |
| Устойчивость к антибот-системам | Не создаёт browser fingerprint (нет WebDriver-флагов, canvas fingerprint, характерных для headless Chrome паттернов) — но требует корректной эмуляции заголовков и cookie-сессии | Больше похож на реального пользователя по поведению рендеринга, но легче детектируется по самим признакам headless-режима без stealth-плагинов |
| Устойчивость к смене вёрстки | Зависит от внутреннего JSON-контракта — как правило заметно стабильнее, чем CSS-классы/DOM-структура, но при обновлении контракта требует ручного реверс-инжиниринга (см. пункт 1 выше) | Зависит от CSS-селекторов и структуры DOM — чаще ломается при редизайне страницы |
| Масштабируемость | Легковесные HTTP-воркеры, легко параллелятся горизонтально (актуально для 50 филиалов, см. пункт 3) | Каждый инстанс браузера — отдельный процесс с заметным потреблением памяти, масштабирование на очереди дороже |
| Инфраструктура (без Docker) | Не требует установки Chromium и системных зависимостей на хосте | Требует Chromium + системные библиотеки — усложняет деплой без контейнеризации, именно то, чего требует ТЗ |
| Риски | Риск полной остановки при существенном изменении контракта до момента ручного обновления парсера | Риск более частых ложных срабатываний антибот-защиты и более высокой стоимости инфраструктуры |

**Выбор: HTTP JSON как основной подход**, реализован в `HttpJsonStrategy`. Он быстрее, легче масштабируется на десятки организаций и не тянет за собой зависимость от headless-браузера на сервере без Docker — что было явным ограничением ТЗ.

Headless-браузер заложен архитектурно как **резервная стратегия** — интерфейс `ReviewSourceStrategy` (`app/Services/Parsing/ReviewSourceStrategy.php`) с единственной сегодняшней реализацией `HttpJsonStrategy` рассчитан на то, что вторая реализация (`HeadlessBrowserStrategy`) может быть подключена без изменения вызывающего кода (`YandexMapParserService`), если/когда основной эндпоинт перестанет быть доступен или начнёт требовать JS-рендеринга.

Важная честная оговорка: реальные внутренние JSON-эндпоинты Яндекс.Карт **не были реверс-инжинирены в рамках этой задачи** (это отдельная и заметная по объёму исследовательская работа, не входившая в ТЗ на архитектуру). `HttpJsonStrategy` реализована по правдоподобному, но гипотетическому контракту (`GET /maps/api/business/{id}/card`, `GET /maps/api/business/{id}/reviews`); вся бизнес-логика (пагинация, лимит 600, идемпотентность, обработка ошибок, детекция поломки разметки) полностью покрыта тестами через `Http::fake()` и корректно работает независимо от точного пути реального эндпоинта. При прогоне против настоящего `yandex.ru` эндпоинт, естественно, не найден — и это ровно тот случай, который правило из пункта 1 обязано поймать: система корректно завершает попытку с `structure_changed`, а не тихо показывает «отзывов нет» (см. живую проверку в истории разработки). Реальное внедрение потребует отдельного этапа реверс-инжиниринга актуального контракта.

### 3. Масштабирование до 50 филиалов

Текущая реализация (очередь `database`, один процесс `queue:work`) выдержит 50 организаций функционально, но не оптимальна по нагрузке на источник и по параллелизму. Список изменений для продакшен-масштаба:

- **Очередь: `database` → Redis.** Драйвер `database` создаёт нагрузку на MySQL на каждый `pop`/`push`/лок и не умеет нормально работать с приоритетами и rate limiting из коробки. Redis (`QUEUE_CONNECTION=redis`) — стандартная рекомендация Laravel для нагрузки выше «пары воркеров», плюс даёт готовую инфраструктуру для `RateLimited`/`WithoutOverlapping` middleware без дополнительных таблиц.
- **Несколько воркеров, но с ограничением конкурентности.** `php artisan queue:work --queue=parsing` можно масштабировать горизонтально (`supervisor`/`systemd`, несколько процессов), но суммарное число одновременных обращений к Яндексу должно быть ограничено явно — иначе рост числа организаций линейно увеличивает нагрузку на источник и вероятность бана. Практическое ограничение: `Illuminate\Queue\Middleware\RateLimited` на уровне очереди `parsing` (например, не более 3–5 одновременных запусков независимо от общего числа организаций) в дополнение к уже реализованному `WithoutOverlapping` per-company (`app/Jobs/ParseYandexCompanyJob.php::middleware()`), который не даёт двум запускам одной и той же организации выполняться параллельно, но не ограничивает общий параллелизм по всем 50 сразу.
- **Laravel Horizon** для наблюдаемости — Redis-очередь плюс Horizon даёт дашборд по throughput, failed jobs, retry-статистике без написания своего мониторинга; для 50 организаций с регулярными перезапусками парсинга это существенно упрощает эксплуатацию (видно, где застряло, что упало, сколько job'ов в очереди).
- **Плановые перезапуски по расписанию.** Сейчас парсинг запускается только вручную из UI (`POST /api/companies/{id}/parse`). При 50 филиалах разумно добавить Laravel Scheduler (`php artisan schedule:run` по cron), который распределённо (не все 50 одновременно, а с равномерным сдвигом в течение дня/часа) ставит задания в очередь — это прямое следствие ограничения конкурентности выше и отдельная небольшая доработка (команда artisan + `withoutOverlapping()`/`onOneServer()` в `Schedule`).
- **БД не является узким местом.** Индексы `unique(company_id, external_id)` и `index(company_id, review_created_at)` на `reviews`, `index(company_id, created_at)` на `parsing_logs` держат upsert и пагинацию быстрыми даже при 50 × 600 ≈ 30 000 строк — партиционирование не требуется на этом объёме.
- **Изоляция сбоев уже заложена**: у каждой организации свой независимый Job и своя история `parsing_logs`, сбой одной не блокирует остальные 49.

### 4. Анти-бан

Реализовано на уровне `HttpJsonStrategy` (`app/Services/Parsing/HttpJsonStrategy.php`) и `ParseYandexCompanyJob`:

- **User-Agent rotation.** Пул реалистичных десктопных UA (`config/yandex_maps.php` → `user_agents`), один случайный UA выбирается один раз на весь запуск парсинга конкретной организации (`UserAgentPool::pickOne()` вызывается в конструкторе стратегии) — сессия остаётся консистентной внутри одного прогона, что важнее «случайности» на каждый запрос: реальный браузер не меняет UA между запросами одной вкладки, и палево именно в такой неестественной смене.
- **Throttling / jitter между страницами.** Между постраничными запросами отзывов одной организации — случайная пауза в диапазоне `throttle_min_seconds`–`throttle_max_seconds` (по умолчанию 1–3 сек, `config/yandex_maps.php`), а не фиксированный интервал: строго равные промежутки — характерный признак бота. Пауза выполняется через инжектируемый интерфейс `Sleeper` (`RealSleeper` в проде, `NullSleeper` в тестах), что позволило протестировать логику троттлинга без реального ожидания в тестах.
- **Ограничение параллелизма на уровне Job.** `WithoutOverlapping` middleware по `company_id` не даёт двум запускам парсинга одной организации выполняться одновременно (см. пункт 3) — это не столько анти-бан, сколько защита от гонки данных, но косвенно снижает пиковую нагрузку на источник.
- **Классификация банов и осмысленный backoff.** HTTP `403`/`429` классифицируются как `SourceBannedException`, `408`/`5xx` — как `SourceTimeoutException` (`HttpJsonStrategy::guardAgainstFailure()`). `ParseYandexCompanyJob` настроен на `$tries = 3` с экспоненциальным `backoff()` → `[30, 120, 300]` секунд — то есть при бане/таймауте система не долбит источник мгновенным повтором, а выжидает нарастающими интервалами.
- **Точка расширения — прокси-пул.** Не реализовано в рамках MVP, но `HttpJsonStrategy` спроектирована так, чтобы добавление ротации исходящего IP (конфигурация пула прокси, передача в `Http::withOptions(['proxy' => ...])`) не требовало изменения вызывающего кода (`YandexMapParserService`, `ParseYandexCompanyJob`) — только конфигурации и, возможно, отдельного провайдера прокси внутри стратегии.

Что было бы правильным добавить при наличии времени: реальный прокси-пул с ротацией по количеству запросов (не только по UA), а также honoring `Retry-After` заголовка, если Яндекс его отдаёт при `429`, вместо фиксированной таблицы backoff.

### 5. Идемпотентность и история изменений

**Идемпотентность отзывов реализована через `updateOrCreate` по составному ключу.** Таблица `reviews` имеет `unique(company_id, external_id)` (миграция `create_reviews_table`), и `ParseYandexCompanyJob::handle()` на каждый полученный от источника отзыв делает:

```php
Review::updateOrCreate(
    ['company_id' => $company->id, 'external_id' => $review->externalId],
    ['author_name' => ..., 'rating' => ..., 'text' => ..., 'review_created_at' => ...],
);
```

Это даёт три свойства одновременно: (1) повторный запуск парсинга той же организации не создаёт дублей — гарантия на уровне уникального индекса, а не только на уровне кода; (2) если текст/оценка отзыва на источнике изменились между запусками, актуальная версия перезапишет старую; (3) upsert выполняется **по мере получения** каждого отзыва из генератора (`YandexMapParserService::fetchReviews()` — ленивая последовательность), а не пачкой в конце — то есть при обрыве соединения на середине сбора уже полученные отзывы остаются сохранёнными, а не теряются целиком (edge case «частичный сбор», spec.md §4).

**История запусков парсинга есть**, история изменений самих отзывов — нет. Таблица `parsing_logs` (`status`, `reviews_collected`, `error_type`, `error_message`, `started_at`, `finished_at`) хранит полную историю всех попыток сбора по каждой организации, включая неудачные — это отвечает на вопрос «когда и с каким результатом запускался парсинг». А вот сама таблица `reviews` хранит только **текущее** состояние: `updateOrCreate` перезатирает `text`/`rating` при изменении, не оставляя следа, каким было предыдущее значение. Даты `created_at`/`updated_at` на `reviews` позволяют ответить «когда мы впервые увидели этот отзыв» и «когда последний раз подтверждали его актуальность», но не «что именно изменилось».

Что было бы правильным добавить при наличии времени — таблицу-снимок изменений (`review_history` / `review_snapshots`): при каждом upsert, если хотя бы одно значимое поле (`text`, `rating`) реально изменилось по сравнению с текущим — писать отдельную строку с предыдущим значением, `changed_at` и, возможно, `parsing_log_id`, к которому относится изменение. Это дало бы полный аудит без переусложнения основной таблицы `reviews` (которая обязана оставаться быстрой для пагинации US-4) и было прямо отмечено как осознанно отложенное расширение уже на этапе планирования ([plan.md §3.4](.sdd/plan.md)).

## Что сделано и что улучшил бы при наличии времени

### Что сделано

- Полный SDD-цикл: спецификация → план → декомпозиция → реализация по фазам, с чек-листом в [.sdd/tasks.md](.sdd/tasks.md).
- Backend (Laravel 11): Sanctum SPA-аутентификация с сид-пользователем; схема БД (`companies`, `reviews`, `parsing_logs`) с индексами под идемпотентность и пагинацию; `YandexMapParserService` + `HttpJsonStrategy` с пагинацией до 600 отзывов, UA rotation, троттлингом, детекцией смены разметки; `ParseYandexCompanyJob` с полным циклом статусов, backoff и классификацией ошибок; REST API (`CompanyController`, `ReviewController`) с валидацией ссылок, дедупликацией организаций и защитой от параллельного запуска парсинга (`409`).
- Frontend (Vue 3 + Vite + Pinia): аутентификация с восстановлением сессии по cookie, защищённые роуты, дашборд с формой добавления организации (клиентская подсказка + серверная валидация), пуллинг статуса парсинга каждые 3 сек с автоостановкой, метрики организации, список отзывов с пагинацией по 50, обработка edge cases (пустой список, отзыв без текста), полная локализация интерфейса на русский язык.
- Тесты: 65 backend (PHPUnit, юнит + feature, через `Http::fake()` — без реальной сети) и 12 frontend (Vitest, сторы с замоканным Axios) — все зелёные.
- Ручная сквозная проверка в реальном браузере против реального backend и реального `yandex.ru`: логин, добавление/дедупликация организации, запуск парсинга, наблюдение статуса через polling, пагинация по 120 тестовым отзывам, логаут. В процессе этой проверки было найдено и исправлено два реальных бага (backend не проставлял `parse_status = pending` сразу при диспетче job'а; фронтенд-стор не синхронизировал элемент списка организаций с обновлённым `currentCompany`).

### Что улучшил бы при наличии времени

- **Реверс-инжиниринг настоящего внутреннего API Яндекс.Карт.** Сейчас `HttpJsonStrategy` реализована по правдоподобному, но не подтверждённому реальным трафиком контракту (см. пункт 2 выше) — это самая существенная незакрытая работа перед реальным продакшен-использованием.
- **`review_history`/`review_snapshots`** для полного аудита изменений отзывов (пункт 5).
- **Redis + Horizon** вместо `database`-очереди, `RateLimited` middleware на уровне очереди `parsing`, плановые запуски по расписанию (Laravel Scheduler) — всё из пункта 3, нужно для реальных 50 филиалов.
- **Прокси-пул с ротацией** и honoring `Retry-After` — пункт 4.
- **Многопользовательский скоуп организаций.** Сейчас (осознанно, см. [plan.md §5](.sdd/plan.md)) все организации общие для всех авторизованных пользователей — для реального многопользовательского продукта нужен `user_id` на `companies` и `Policy` с проверкой владения (задел под это оставлен в задаче 4.7 из [tasks.md](.sdd/tasks.md), но не реализован, так как ТЗ явно допускает MVP-упрощение).
- **E2E-тесты (Playwright/Cypress)** поверх реального связанного стека backend+frontend — сейчас сквозной путь проверен только вручную через браузерную автоматизацию в процессе разработки, автоматизированного E2E-прогона в CI нет.
- **Публикация backend-сообщений об ошибках на русском.** Frontend локализован полностью, но конкретные сообщения об ошибках, приходящие от Laravel (валидация, `auth.failed`, тексты исключений парсера), остаются на английском — на фронтенде есть точечный словарь известных сообщений ([frontend/src/i18n/apiMessages.js](frontend/src/i18n/apiMessages.js)), но полноценная локализация уровня backend (`lang/ru`) не сделана.

## Известные ограничения (MVP-допущения)

Эти пункты — не забытые баги, а осознанные упрощения объёма для MVP, зафиксированные ещё на этапе планирования ([plan.md §5](.sdd/plan.md)):

- **Организации общие для всех пользователей.** В схеме `companies` нет `user_id` — любой авторизованный пользователь видит и может запускать парсинг для всех добавленных организаций. Для многопользовательского продукта это первое, что нужно менять.
- **Нет полной истории изменений отзывов.** `reviews.text`/`reviews.rating` хранят только актуальное значение; при изменении отзыва на источнике старое значение перезаписывается без следа (см. пункт 5 выше). История *запусков* парсинга (`parsing_logs`) при этом есть в полном объёме.
- **Запуск парсинга только вручную.** Нет планового/периодического перезапуска по расписанию — пользователь должен сам нажать «Запустить сбор отзывов» на каждую организацию; это осознанно не входило в MVP-скоуп (см. пункт 3 выше про Laravel Scheduler как возможное расширение).
